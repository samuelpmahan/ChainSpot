# Propose Skill

You have a list of skills. Sometimes a task wants one that isn't on it —
not "this would be nice to have," but a real, recurring shape of work with
no home. This skill is what to do in that moment, instead of either quietly
freehanding it or letting the feeling evaporate unmentioned.

## The bar

Most tasks that feel unusual are still one-offs, and one-offs don't need a
skill — they need you to just do the task well. Propose only when at least
one of these is true:

- the same missing specialization came up more than once in this task alone
- the discipline is clearly generalizable — the next time this kind of task
  shows up, in this project or another, the same process would apply
  unchanged
- the user's own phrasing already names the gap ("I need something for
  X," a correction that repeats a theme from earlier in the conversation)

A single odd task that won't come back isn't a skill. Don't propose one for
it — do the task, note nothing, move on.

## Before proposing, check you're not duplicating

Look at your actual current skill list first. The gap has to survive that
check — it's easy to feel like nothing covers a task when the real issue is
just not recognizing that an existing skill's description already does,
under a name that doesn't obviously match. If something close exists, either
use it or say plainly that it's close-but-not-quite and why, rather than
proposing a near-duplicate.

## What a good proposal contains

Same bar as any skill built well: grounded in something specific, not a
generic category.

- **A candidate name.**
- **One sentence on what discipline it would encode** — the actual rules,
  not just the domain ("checks readiness and explains tickets in plain
  language before triaging a backlog," not "a ticket skill").
- **The concrete moment that revealed the gap** — a quote, a decision point,
  a correction, a repeated pattern. If you can't point to one, you likely
  haven't hit the bar above yet.

## How to surface it

Don't interrupt the task to raise this. Finish the current response, or
reach a natural stopping point, first. Then:

- If the environment provides a way to flag an out-of-scope suggestion as
  its own background item without derailing the conversation (in Claude
  Code, that's the task-spawning tool that produces a chip the user can act
  on or ignore) — use it, with a title, a one-line plain-English reason, and
  a self-contained prompt that names the concrete moment above.
- If no such mechanism exists, add a short trailing note at the end of your
  response instead — a sentence or two, not a pitch.

Either way: propose, then wait. Never build the skill unprompted just
because the gap seems obvious to you — that's the same unrequested scope
creep a lazy-code discipline would reject in production code, applied to
your own process instead of the user's code.
