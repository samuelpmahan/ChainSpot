# APGD ribbon-kernel transport audit

This note supersedes the **interpretation** of feature-specific numbers in `apgd-ribbon-kernels.md`. The original file remains the reproduction record of the synthetic-hard-rival discovery run.

## Contamination correction

The original scaffold constructed false candidates by joining onto neighboring **real annotated ribbons**. That makes ribbon-likeness unusually diagnostic by construction. Therefore the original headline values for `contrast_frac_low`, `paired_edge_q25`, exact badge-leg split, and one-to-one improvement cannot be treated as unbiased ownership estimates.

With only four dev courses, differences smaller than roughly five holes are also treated as tied. In particular, 55/56/57/58 is one performance cluster, not four findings. The original longitudinal rank shuffles and hard-negative-mining collapse are not promoted: both are too entangled with the synthetic rival generator to support a transferable conclusion.

Before real-D08 falsification, only these claims survived:

1. **Truth-free relative calibration** is physically motivated because basemap/render intensity is a nuisance variable.
2. **Tail aggregation deserves testing against mean aggregation**; the transferable hypothesis is lower-tail/persistence testimony, not either named scalar.
3. **Non-monotone capacity should be shallow and capped**: quadratic or a tiny spline, no high-capacity search.
4. **Tee->Badge and Badge->Basket are different ownership objects**, and one-to-one endpoint ownership is a hard structural constraint. The synthetic effect size is not trusted.

## Real-D08 falsifier

Commit path: `scripts/chainspot-lab/apgd-d08-falsify.ts`.

Protocol:

- D08 candidates/rivals are generated by the existing `scripts/nuthing/pair-matrix.ts` from the exact dev rasters.
- For each measurable hole, compare the truth row with D08's **actual strongest false competitor**.
- Object masking uses detected badges/tees/baskets only; truth coordinates are not used by the two tested kernels.
- `contrast_frac_low`: lower is better.
- `paired_edge_q25`: higher is better.
- Diagnostic D08 images are deleted after each run; retained experiment images = 0.

Observed head-to-head result:

| Rival set | n | contrast truth wins + ties | half-credit | paired-edge truth wins + ties | half-credit |
|---|---:|---:|---:|---:|---:|
| all measurable | 69 | 49 + 9 | **53.5/69** | 46 + 3 | **47.5/69** |
| shares same tee | 32 | 23 + 5 | **25.5/32** | 21 + 2 | **22/32** |
| shares same basket | 21 | 12 + 4 | **14/21** | 12 + 1 | **12.5/21** |
| shares neither | 16 | 14 + 0 | **14/16** | 13 + 0 | **13/16** |

Per course:

- DashsTrack: n=18; contrast 15/18 half-credit; paired 13/18.
- HeritagePark: n=15; contrast 11/15; paired 10/15. Three comparisons had too little profile outside the truth-free object mask and are intentionally omitted rather than imputed.
- Lenard: n=18; contrast 11/18; paired 11/18 half-credit.
- TowneLake: n=18; contrast 16.5/18; paired 13.5/18.

The important falsification result is **not** that either scalar is now a production feature. It is that both retain substantial discrimination on real D08 ribbon-vs-ribbon confusions, including same-tee and same-basket rivals. The synthetic scaffold therefore did not manufacture the entire phenomenon.

## Promotion decision

Proceed with exactly one conservative dev-fit -> validation model specification:

- real D08 dev candidates only;
- separate Tee->Badge and Badge->Basket leg testimony;
- badge + course relative rank calibration;
- support mean plus lower-tail/persistence summaries;
- multiscale 30/37/40 px median for the two transverse profile kernels so validation does not receive a truth-derived corridor width;
- one centered quadratic coordinate per signal, no RBF/spline search;
- fixed pairwise Ridge lambda=2 and top-8 real D08 rivals per badge;
- separate one-to-one tee and basket assignment.

LOCO on dev is a sanity check only. It does **not** choose a second configuration. The model is then refit on all annotated dev data and frozen before reading `chainspot-corpus/validation`.

Validation contains no annotation JSON in the public corpus. The validation process therefore emits blind predictions, margins, and one final prediction image per course; it makes no validation-accuracy claim unless an external sealed evaluator scores those predictions.
