# ChainSpot Lab foundation contracts

This document fixes the identity and persistence rules implemented by the
first bootstrap step. A **Replay Node** is one deterministic measurement or
decision stage whose output can be reused without rerunning its parents.

## Experiment versus run

- `experimentHash` is deterministic. It hashes the resolved manifest, resolved
  suite, and exact implementation-registry resolution.
- `runId` is a new UUID for every execution attempt.

Therefore a cold execution and a cache-hit replay share one experiment hash
but remain two historical runs with separate host, timing, and cache records.

## Historical implementation behavior

Infrastructure must not generalize an existing algorithm merely to make a
race rectangular. A historical course/implementation combination may emit
`not_applicable` with a reason. A generalized algorithm requires a new
implementation ID/version; for example, a profile-derived recovery would not
reuse the historical `consensus50-v1` identity.

## Implementation source identity

Each registry entry declares its complete behavior-bearing source set. This
includes the algorithm, its execution adapter, and imported shared algorithm
files. The source digest hashes that declared set.

Do not hash unrelated repository files. A CSS edit must not invalidate CV
evidence; a change to `endpoints.ts` must invalidate nodes that declare it.

## Stable entities and lineage

An entity has two identity layers:

1. a semantic local ID generated by its producing node, never a run-local
   array position;
2. the immutable producer-object hash.

The durable entity key is `(producerObjectHash, localId)`. Explicit lineage
edges connect entities across nodes, allowing later queries to follow:

```text
component -> tee candidate -> recovery hypothesis -> merged endpoint
```

The same convention extends to pairs and assignments without changing the
foundation schema.

## Oracle observations and disagreements

Oracle-reviewed plausible misses, hard negatives, and implementation
disagreements are immutable evidence. An observation is stored as a
content-addressed `oracle.observation.v1` object and indexed by a stable case
ID plus integer version. A correction creates a new object that points to the
superseded object; the earlier review is retained.

Each observation preserves:

- the candidate/entity and upstream evidence objects that prompted review;
- source crops, overlays, or rasters as immutable artifact objects;
- classification, optional corrected geometry, rendering-layer attribution,
  reviewer provenance, notes, and multiple tags/slices.

Oracle roles are limited to `discovery` and `calibration`. Ordinary truth sets
use a separate table and may be marked `held_out_validation`, preventing
reviewed cases from silently becoming untouched validation evidence.

## Historical combination races

A manifest may declare multiple swappable decision axes. The resolved race is
the Cartesian product of those axes: every selection from axis A is paired
with every selection from axis B, and so on. Every resolved combination gets
a deterministic hash and a recorded compatibility result.

There is no champion field or implicit substitution. Historical variants stay
addressable through their registry identities. Oracle evaluation records join
an observation, a run, and an implementation-combination hash, enabling later
queries such as “how did every compatible historical stack behave on all
`basket-overlap` and `<=30-surviving-px` observations?”

## Immutable objects and cache entries

Large payloads live in the filesystem object store. SQLite contains identity,
lineage, searchable metadata, metrics, and references. Objects are written to
a temporary directory and atomically published under their SHA-256-derived
path. Existing objects and cache-key mappings are never overwritten.
